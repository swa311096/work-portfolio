# SPL Interview Proposal Template

A repeatable framework for turning any ambiguous project prompt into a concise memo plus operating model.

Core rule:

> The memo should be a concise client-facing proposal. The spreadsheet should carry the detailed assumptions, ramp, QA, task allocation, and economics.

## 1. Two-Hour Game Plan

Use this sequence when the case gives limited time, ambiguous scope, and asks for a proposal plus supporting analysis.

| Time | What to do | Output |
|---|---|---|
| 0-10 min | Read the prompt; identify client, goal, constraints, and required deliverables. | One-sentence thesis |
| 10-25 min | Choose the project scope and data/product/service type. | Clear pilot recommendation |
| 25-45 min | Draft the concise client-facing memo. | Proposal draft |
| 45-85 min | Build the spreadsheet appendix. | Ramp, staffing, QA, pricing |
| 85-105 min | Add risks, assumptions, next steps, and polish numbers. | Defensible plan |
| 105-120 min | Final consistency check across memo and spreadsheet. | Client-ready deliverable |

## 2. Universal Case Logic

Almost every SPL-style project proposal can be answered with seven questions. If the case feels unfamiliar, use these as the backbone.

| Question | What the answer should show |
|---|---|
| 1. What should the client do? | A specific recommendation, not a menu of options. |
| 2. Why this scope? | A rationale for the domain, workflow, customer segment, or use case. |
| 3. What exactly will be delivered? | The concrete output: records, workflows, reviews, datasets, pilots, or milestones. |
| 4. Who will do the work? | Expert archetypes, sourcing, vetting, staffing, and review roles. |
| 5. How will quality be controlled? | QA layers, acceptance criteria, review model, and quality metrics. |
| 6. How will the project ramp? | Phases, timeline, staffing ramp, weekly output, and delivery milestones. |
| 7. How does the company make money? | Pricing model, cost assumptions, target margin, and expansion path. |

## 3. Concise Client-Facing Memo Template

The memo should be one to two pages. It should not include every operational detail; it should point to the spreadsheet for the project plan and economics.

From: `[Company Name]`  
To: `[Client / Customer Team]`  
Re: Project Proposal: `[Project Name]`  
Date: `[Insert Date]`

`[Company]` proposes a `[X-week]` pilot to help `[Client]` achieve `[business objective]`. The pilot will focus on `[specific domain/workflow/customer segment]` and will deliver `[specific output]`. We recommend this approach because it creates a measurable foundation for `[client goal]`, while limiting scope risk and allowing both teams to validate quality before expanding into a larger program.

As part of this pilot, `[Company]` will deliver `[number]` accepted `[deliverable type]` across `[scope areas]`. Initial coverage will include `[Area 1]`, `[Area 2]`, `[Area 3]`, `[Area 4]`, and `[Area 5]`. Each accepted deliverable will include `[brief description of components]`, with detailed task definitions and acceptance criteria included in the attached project plan.

We recommend starting with `[chosen scope/domain]` because it is `[Reason 1]`, `[Reason 2]`, and `[Reason 3]`. This scope is large enough to generate meaningful signal, but narrow enough to allow for clear quality control, expert calibration, and reliable delivery within the pilot timeline. After the pilot, future phases can expand into `[Expansion Area 1]`, `[Expansion Area 2]`, and `[Expansion Area 3]`.

`[Company]` will staff the project using a dedicated team of `[expert type / operator type / reviewer type]`. The team will include `[creator/operator role]`, `[reviewer/manager role]`, and `[senior reviewer/QA lead role]`. Experts will be sourced through `[sourcing channels]` and vetted through `[screening method]`, `[work sample]`, and `[calibration process]`. The attached project plan outlines the detailed expert ramp, task allocation, and review model.

To ensure quality, `[Company]` will run a structured production process across `[three/four]` stages: `[Stage 1]`, `[Stage 2]`, `[Stage 3]`, and `[Stage 4]`. Each output will become delivery-ready only after it meets defined acceptance criteria for `[accuracy]`, `[completeness]`, `[format]`, and `[client relevance]`. We will track quality through weekly metrics, including `[metric 1]`, `[metric 2]`, `[metric 3]`, and `[metric 4]`.

`[Company]` will price the pilot using a `[pricing model: per accepted output / expert-hour / milestone / hybrid]` model. This aligns incentives around `[quality / speed / accepted output]` while allowing `[Company]` to manage staffing, review, and delivery economics internally. The attached model includes the detailed cost assumptions, target margin, weekly ramp, quality controls, and delivery milestones.

As next steps, we ask `[Client]` to confirm `[Decision 1]`, `[Decision 2]`, and `[Decision 3]`. Upon approval, `[Company]` can begin setup immediately and deliver the first calibrated sample batch within `[timeframe]`.

## 4. Spreadsheet Appendix Template

For a two-hour case, five to six tabs are enough. The spreadsheet should support the memo, not duplicate it.

| Tab | Purpose | Must include |
|---|---|---|
| 1. Executive Summary | One-page operating overview. | Pilot length, deliverable, scope, team size, QA model, pricing model, target margin, expansion path. |
| 2. Scope / Domain Selection | Show structured judgment on where to start. | Options, scoring criteria, recommendation, rationale. |
| 3. Deliverable / Task Breakdown | Show what work will actually be produced. | Workstreams, volume, % mix, complexity, notes. |
| 4. Expert / Staffing Ramp | Show how capacity scales over time. | Phases, weeks, team size, weekly output, cumulative output. |
| 5. Quality Control | Show how the output becomes trustworthy. | QA steps, owners, coverage %, quality metrics and targets. |
| 6. Pricing / Economics | Show how the company makes money. | Output volume, hours/output, cost, overhead, margin, client price. |

## 5. Sample Tables To Recreate Quickly

These are the tables to recreate quickly in Excel and adapt to the case.

### Executive Summary

| Item | Recommendation |
|---|---|
| Pilot length | `[8-12 weeks]` |
| Deliverable | `[X accepted outputs / records / workflows]` |
| Scope | `[Domain or workflow]` |
| Expert/team size | `[X people]` |
| QA model | `[Calibration + review + rework + audit]` |
| Pricing model | `[Per accepted output / hourly / hybrid]` |
| Target margin | `[35-45%]` |
| Expansion path | `[Future phases]` |

### Scope / Domain Selection

Simple scoring works well: 1 = low, 3 = medium, 5 = high. The goal is not perfect math; the goal is structured decision-making.

| Option | Client relevance | Ease of staffing | Quality risk | Revenue potential | Recommendation |
|---|---|---|---|---|---|
| Option A | High | Medium | Medium | High | Yes |
| Option B | Medium | High | Low | Medium | No |
| Option C | High | Low | High | High | No |

### Deliverable / Task Breakdown

| Workstream | % of total | Output volume | Complexity | Notes |
|---|---:|---:|---|---|
| Workflow 1 | 25% | 500 | Medium | Core use case |
| Workflow 2 | 20% | 400 | High | Requires senior review |
| Workflow 3 | 20% | 400 | Medium | High-volume category |
| Workflow 4 | 20% | 400 | Low | Easier to ramp |
| Workflow 5 | 15% | 300 | High | Escalation / edge cases |

### Ramp Plan

| Phase | Weeks | Team size | Weekly output | Cumulative output | Focus |
|---|---|---|---|---|---|
| Setup / calibration | 1-2 | 10-20 | 50-100 | 100 | Templates, sample batch, QA alignment |
| Controlled production | 3-5 | 30-50 | 150-250 | 700 | Ramp experts, test quality |
| Scaled production | 6-10 | 60-100 | 300-400 | 1,800 | Main production |
| Final audit / delivery | 11-12 | 30-50 | 100-200 | 2,000 | Rework, audit, final delivery |

### Quality Control

| QA step | Owner | % covered | Purpose |
|---|---|---:|---|
| Work sample / calibration | Senior reviewer | 100% of experts | Vet quality before production |
| First-pass review | Reviewer | 100% of outputs | Check accuracy and completeness |
| Double review | Senior reviewer | 15-25% sample | Measure reviewer consistency |
| Rework loop | Creator + reviewer | As needed | Fix rejected work |
| Final audit | QA lead | 5-10% sample | Catch systemic issues before delivery |

| Metric | Target |
|---|---|
| Acceptance rate | 80-90% after calibration |
| Rework rate | <20% after week 3 |
| Reviewer disagreement rate | <10-15% |
| On-time delivery | >95% |
| Final audit defect rate | <5% |

### Pricing / Economics

| Item | Assumption / Formula |
|---|---|
| Accepted outputs | `[X]` |
| Hours per accepted output | `[X]` |
| Total expert hours | Accepted outputs x hours/output |
| Blended expert cost | `[$X/hour]` |
| Total expert cost | Total hours x blended rate |
| Program overhead | `[10-15% of expert cost]` |
| Total cost | Expert cost + overhead |
| Target gross margin | `[35-45%]` |
| Client price | Total cost / (1 - target margin) |
| Price per accepted output | Client price / accepted outputs |

Formula to remember:

> Client Price = Total Cost / (1 - Target Gross Margin). Example: if total cost is $900K and target margin is 40%, client price = $1.5M.

## 6. Useful Default Assumptions

If the prompt does not give numbers, use reasonable assumptions and label them clearly.

| Area | Reasonable assumption |
|---|---|
| Human data / AI eval project | 1,000-3,000 accepted records |
| Expert review project | 500-2,000 reviewed outputs |
| Marketplace supply project | 50-200 active experts |
| Enterprise workflow pilot | 8-12 weeks |
| Acceptance rate after calibration | 80-90% |
| Double-review sample | 15-25% |
| Final audit sample | 5-10% |
| Expert-heavy services margin | 30-45% gross margin |
| Strategic first pilot margin | 25-35% acceptable if expansion is large |

## 7. Choosing The Pricing Model

| Pricing model | Use when | Pros | Cons |
|---|---|---|---|
| Per accepted output | Deliverable is measurable | Aligns incentives around quality | Company takes productivity risk |
| Expert-hour model | Scope is uncertain | Easy to justify | Can look like staffing |
| Milestone-based | Client wants predictability | Clean enterprise pricing | Requires clear milestones |
| Hybrid | Scope has uncertainty but output matters | Balanced | Slightly more complex |

Operator answer:

> Best default: use a per-accepted-output model for the client, with expert-hour economics managed internally. This gives the client clarity while letting the company manage productivity, staffing, and margin.

## 8. Risk Register Template

| Risk | Why it matters | Mitigation |
|---|---|---|
| Scope ambiguity | Outputs may become inconsistent. | Align on taxonomy and sample batch before scale. |
| Expert quality variance | Poor work creates rework. | Use work samples, calibration, and tiered task access. |
| Ramp delay | Delivery timeline may slip. | Build a larger candidate funnel than needed. |
| QA bottleneck | Review capacity may constrain production. | Separate creator and reviewer pools. |
| Client review delays | Calibration may stall. | Pre-schedule weekly review checkpoints. |
| Margin compression | Rework increases costs. | Track rework rate and adjust expert access. |

## 9. Reusable Language Blocks

Opening paragraph formula:

> `[Company]` proposes a `[timeline]` pilot to help `[Client]` achieve `[objective]`. The pilot will focus on `[specific scope]` and deliver `[specific output]`. We recommend this approach because it creates `[measurable value]` while limiting `[key risk]` and establishing a foundation for `[future expansion]`.

Why this scope formula:

> We recommend starting with `[scope]` because it is `[client-relevant]`, `[measurable]`, and `[operationally feasible]`. It is broad enough to produce useful signal, but narrow enough to support expert calibration, quality control, and delivery within the pilot timeline.

Quality formula:

> Quality will be managed through a staged production process: calibration, production, expert review, rework, and final audit. No output will be considered accepted until it meets defined criteria for accuracy, completeness, format, and client relevance.

Next steps formula:

> As next steps, we ask `[Client]` to confirm `[scope]`, `[working environment]`, and `[review cadence]`. Upon approval, `[Company]` can begin setup immediately and deliver the first calibrated sample batch within `[timeframe]`.

## 10. Interview Talking Track

If asked to walk through the proposal, use this structure:

> I started by narrowing the problem to a pilot that is useful but manageable. My recommendation is to begin with a measurable evaluation layer rather than trying to produce every possible output at once. The memo gives the client the high-level proposal, while the spreadsheet shows the operating plan: task allocation, expert ramp, QA process, and economics. The main tradeoff is scope versus quality. I would rather deliver a narrower, highly reviewed project that the client trusts than a broader project with unclear quality. If the pilot works, the same operating model can expand into a larger program.

## 11. What To Avoid

| Avoid | Why it hurts the proposal |
|---|---|
| Overly long memo | Client-facing proposal becomes hard to read. |
| Too much research | Can look like inability to make decisions under ambiguity. |
| No numbers | Proposal feels hand-wavy. |
| No QA system | Enterprise client will not trust delivery. |
| Instant full ramp | Operationally unrealistic. |
| Pricing only by hourly labor | Makes the company look like a staffing vendor. |
| No expansion path | Misses the account growth angle. |
| Too many tabs | Looks overbuilt for a timed case. |

## 12. Final Deliverable Checklist

- Memo is one to two pages, client-facing, and recommendation-driven.
- Memo gives the "what" and "why"; spreadsheet gives the "how" and "how much."
- Spreadsheet has five to six clear tabs, not an overbuilt model.
- The ramp plan is phased rather than assuming immediate scale.
- The QA model includes calibration, review, rework, and audit.
- The pricing model includes cost, margin, and client price.
- Risks are acknowledged with practical mitigations.
- The recommendation is specific enough to defend in discussion.

Final reminder: the interviewer is not looking for the perfect answer. They are looking for judgment under ambiguity, clear communication, and an operating plan that could actually work.
